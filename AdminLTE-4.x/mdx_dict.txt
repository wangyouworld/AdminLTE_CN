## What is AdminLTE?
## 什么是 AdminLTE？
AdminLTE is a free, MIT-licensed admin dashboard template built on **Bootstrap 5.3.8** with vanilla TypeScript (no jQuery). It ships responsive layouts, a sidebar navigation system, light/dark/auto color mode, RTL support, and a growing catalog of demo pages — calendar, kanban, chat, file manager, invoice, profile, settings, and more.
AdminLTE 是一个免费的、基于 MIT 许可证的后台管理面板模板，基于 **Bootstrap 5.3.8** 构建，使用原生 TypeScript（无 jQuery）。它提供了响应式布局、侧边栏导航系统、亮色/暗色/自动颜色模式、RTL 支持，以及不断增加的示例页面——日历、看板、聊天、文件管理器、发票、个人资料、设置等。
It's a *template*, not a component library. You drop the markup into your own project (or framework templates) and customize the parts you need. Bootstrap 5 handles the components; AdminLTE provides the application shell.
它是一个*模板*，而不是组件库。将代码放在项目（或框架模板）中，并自定义所需部分。Bootstrap 5 负责组件；AdminLTE 提供应用外壳。
If you've never used AdminLTE before, start with [Getting Started](getting-started.html) — it walks through a working dashboard in ten minutes.
如果您从未使用过 AdminLTE，请从[入门指南](getting-started.html)入手——它会在十分钟内带您完成一个可用的仪表盘。

##### Body 级布局修饰符
Layout behaviour is mostly controlled by classes on `<body>`, not `.app-wrapper`. The supported modifiers:

| Class | What it does |
| 类名 | 作用 |
| `layout-fixed` | Sidebar gets its own scrollbar; only `.app-main` scrolls with the page |
| `layout-fixed` | 侧边栏拥有自己的滚动条；只有 `.app-main` 随页面滚动 |
| `fixed-header` | Sticky `.app-header` at the top; sidebar also pins (since v4.0.0) |
| `fixed-header` | 将 `.app-header` 固定在顶部；侧边栏也会固定（自 v4.0.0 起） |
| `fixed-footer` | Sticky `.app-footer` at the bottom |
| `fixed-footer` | 将 `.app-footer` 固定在底部 |
| `sidebar-expand-{sm,md,lg,xl,xxl}` | Breakpoint at which the sidebar transitions from off-canvas (mobile) to inline (desktop). `lg` is the default in the demos. |
| `sidebar-expand-{sm,md,lg,xl,xxl}` | 侧边栏从 off-canvas（移动端）切换为 inline（桌面端）的 breakpoint。演示中默认使用 `lg` |

##### Responsive behaviour
##### 响应式行为
At and above your `sidebar-expand-*` breakpoint, the sidebar is **inline** — visible in the grid alongside `.app-main`. Below the breakpoint, it becomes **off-canvas** — hidden by default and slid in from the left when the user clicks the hamburger toggle.
在 `sidebar-expand-*` breakpoint 及以上，侧边栏为 **inline** 状态——在网格中与 `.app-main` 并排可见。低于 breakpoint 时，它变为 **off-canvas** 状态——默认隐藏，当用户点击汉堡菜单按钮时从左侧滑入。
Mobile-specific classes:
移动端专用类：
| Class | When applied | Effect |
| 类名 | 应用时机 | 效果 |
| `sidebar-open` | Body — when the user explicitly opens the mobile sidebar | Slides the sidebar in over the content with an overlay |
| `sidebar-open` | Body——当用户主动打开移动端侧边栏时 | 侧边栏带遮罩层从内容上方滑入 |
| `sidebar-collapse` | Body — set automatically when the user closes the mobile sidebar | Hides the sidebar |
| `sidebar-collapse` | Body——当用户关闭移动端侧边栏时自动设置 | 隐藏侧边栏 |
These are managed by the [PushMenu plugin](javascript/pushmenu.html) — you don't write them yourself.
这些由 [PushMenu 插件](javascript/pushmenu.html)管理——您无需自己编写。
##### Common pitfalls
##### 常见问题
- **Forgetting `.container-fluid` inside `.app-content`** — the content lands flush against the screen edge. Wrap your content cards in a container.
- **忘记在 `.app-content` 内部添加 `.container-fluid`** ——内容会紧贴屏幕边缘。请将内容卡片包裹在容器中。
- **Putting the sidebar toggle outside `.app-header`** — it'll still work, but the styling expects the navbar context.
- **将侧边栏切换按钮放在 `.app-header` 外部** ——它仍然可以工作，但样式预期是放在导航栏上下文中。
- **Mixing `.app-*` and `.main-*` classes** — `.main-*` is the AdminLTE 3 naming. Don't combine them. See [Migration from v3](migration.html).
- **混用 `.app-*` 和 `.main-*` 类** ——`.main-*` 是 AdminLTE 3 的命名方式。不要将它们组合使用。参见[从 v3 迁移](migration.html)。
- **Using `position: fixed` on something inside `.app-main`** — `layout-fixed` already gives `.app-main` `overflow: auto`. Children with `position: fixed` may behave unexpectedly. Use sticky positioning instead.
- **在 `.app-main` 内部的元素上使用 `position: fixed`** ——`layout-fixed` 已经为 `.app-main` 设置了 `overflow: auto`。使用 `position: fixed` 的子元素可能会出现意外行为。请改用粘性定位。
- **Hardcoding sidebar width in custom CSS** — the sidebar width is exposed via the SCSS variable `$lte-sidebar-width`. If you need to know it from JavaScript, read the rendered `.app-sidebar` element's computed width.
- **在自定义 CSS 中硬编码侧边栏宽度** ——侧边栏宽度通过 SCSS 变量 `$lte-sidebar-width` 暴露。如果需要在 JavaScript 中获取它，请读取渲染后的 `.app-sidebar` 元素的计算宽度。

##### What doesn't flip
##### 不翻转的内容
- Bootstrap Icons (SVG glyphs) — most icons are direction-neutral; arrows that *do* indicate direction (`bi-arrow-right`, `bi-chevron-right`, etc.) need to be manually swapped to their `-left` siblings.
- Bootstrap Icons（SVG 字形）——大多数图标是方向中性的；确实指示方向的箭头（`bi-arrow-right`、`bi-chevron-right` 等）需要手动替换为对应的 `-left` 版本。
- Inline images, charts, and third-party widgets — their internal layout doesn't react to `dir`. Check each integration (ApexCharts, FullCalendar, Tabulator) for an RTL option.
- 内联图片、图表和第三方小部件——它们的内部布局不会对 `dir` 做出响应。请检查每个集成（ApexCharts、FullCalendar、Tabulator）是否有 RTL 选项。
- Numbers — digits stay LTR even in RTL contexts (this is standard Unicode bidi behaviour, not a bug).
- 数字——即使在 RTL 上下文中，数字仍然保持 LTR（这是标准的 Unicode 双向文本行为，不是 Bug）。
##### Common gotchas
##### 常见问题
- **The `.min.css` minified RTL build is `.rtl.min.css`, not `.min.rtl.css`.** Filename order matters; the build script emits the former.
- **压缩后的 RTL 构建文件是 `.rtl.min.css`，而不是 `.min.rtl.css`。** 文件名顺序很重要；构建脚本生成的是前者。
- **Don't mix LTR and RTL stylesheets on the same page** — pick one. If you need a mixed-direction app, use `dir="rtl"` on the relevant subtree, not a separate stylesheet.
- **不要在同一页面上混合使用 LTR 和 RTL 样式表** —— 选择其一。如果您需要混合方向的应用，请在相关的子树上使用 `dir="rtl"`，而不是使用单独的样式表。
- **Icon mirroring**: when you swap an icon for RTL, also update its `aria-label` if it indicates direction (eg. "Next page" should still say "Next page" — only the glyph rotates).
- **图标镜像**：当您为 RTL 替换图标时，如果它指示方向，也要更新其 `aria-label`（例如 "Next page" 仍应显示为 "Next page" —— 只有字形发生变化）。

##### Production vs source

The plugins live in [`src/ts/`](https://github.com/ColorlibHQ/master/src/ts) as TypeScript modules. The published `dist/js/adminlte.js` is a Rollup bundle of all seven, exporting them under a single `adminlte` namespace (UMD) or named imports (ESM).

The Layout plugin manages CSS transitions during layout changes and signals when the app has finished loading.
Layout 插件负责管理布局变化期间的 CSS 过渡动画，并在应用加载完成时发出信号。
##### Behavior
##### 行为
The Layout plugin performs two key tasks automatically:
Layout 插件自动执行两项关键任务：
1. **Hold Transitions** - During window resize, CSS transitions on the sidebar, navbar, and content area are temporarily disabled to prevent visual glitches. The `hold-transition` class is added to `<body>` for the duration.
1. **暂停过渡动画** —— 在窗口大小调整期间，侧边栏、导航栏和内容区域的 CSS 过渡动画会被暂时禁用，以防止视觉闪烁。在此期间，`hold-transition` 类会被添加到 `<body>` 上。
2. **App Loaded Signal** - After a 400ms delay on DOMContentLoaded, the `app-loaded` class is added to `<body>`. Use this class in CSS to defer animations until the app is ready, preventing flicker on initial page load.
2. **应用加载完成信号** —— 在 DOMContentLoaded 事件触发后延迟 400ms，`app-loaded` 类会被添加到 `<body>` 上。在 CSS 中使用此类可将动画延迟到应用准备就绪之后，从而防止初始页面加载时的闪烁。

##### Extra colours moved to an opt-in stylesheet

AdminLTE 3 在主 CSS 里塞了一大堆一次性的颜色类（`.bg-navy`、`.bg-purple`、`.bg-fuchsia`、`.bg-gradient-*`，还有侧边栏/导航栏皮肤）。到了 v4，核心样式表只认 Bootstrap 的主题色；扩展调色板成了一个独立的、按需启用的文件 `dist/css/adminlte-colors.css`，里面是一套重新设计过的十四种颜色（每一种配白色文字对比度都 ≥ 4.5:1），并且每种颜色都配齐了同样的类系列 —— `.bg-*`、`.text-bg-*`、`.bg-gradient-*`、`.card-*`、`.callout-*`……。

##### What to deploy

##### Cache headers
##### 缓存头
The dist artefacts have content hashes in their filenames *only if you wire it up via your bundler* — AdminLTE itself ships fixed filenames. Two reasonable strategies:
构建产物的文件名是否包含内容哈希，*取决于您是否通过构建工具进行配置*——AdminLTE 默认使用固定文件名。以下是两种合理的做法：
**Short cache + version query string** (simple, works without a build pipeline):
**短缓存 + 版本查询字符串**（简单，无需构建流程即可工作）：
Set `Cache-Control: public, max-age=86400` (1 day) at the server. Bump `?v=` on every release to force cache invalidation.
在服务器上设置 `Cache-Control: public, max-age=86400`（1 天）。每次发布时更新 `?v=` 以强制缓存失效。
**Fingerprinted filenames** (production-grade, requires a bundler):
**指纹文件名**（生产级，需要打包工具）：
Let your bundler emit `adminlte.[hash].min.css` and reference that hash in your HTML. Set `Cache-Control: public, max-age=31536000, immutable` (1 year). This is what Vite/Webpack/Rollup do by default if you import AdminLTE through them.
让你的打包工具生成 `adminlte.[hash].min.css` 并在 HTML 中引用该哈希值。设置 `Cache-Control: public, max-age=31536000, immutable`（1 年）。如果你通过 Vite/Webpack/Rollup 导入 AdminLTE，它们默认就是这样做的。

##### Defer or async?
##### Defer 还是 async？
The AdminLTE bundle waits for `DOMContentLoaded` before wiring its data API, so `defer` is safe and recommended:
AdminLTE 包会在 `DOMContentLoaded` 之后再挂载其 data API，因此 `defer` 是安全且推荐的：
Don't use `async` — the script could execute before its dependencies (Bootstrap, Popper) have parsed, and listeners would attach to elements that don't exist yet.
不要使用 `async`——脚本可能会在其依赖（Bootstrap、Popper）解析完成之前执行，而监听器会附加到尚不存在的元素上。

##### A note on Cloudflare cache

Every component follows the same Bootstrap-style contract:
每个组件都遵循与 Bootstrap 相同的约定：
- `Component.getInstance(element)` — the instance created for that element, or `null`.
- `Component.getInstance(element)` —— 返回该元素对应的实例，若不存在则返回 `null`。
- `Component.getOrCreateInstance(element, config?)` — reuse or create (config only applies on creation).
- `Component.getOrCreateInstance(element, config?)` —— 复用已有实例或新建一个（`config` 仅在新建时生效）。
- `instance.dispose()` — unregister the instance; `getInstance()` returns `null` afterwards.
- `instance.dispose()` —— 销毁实例；调用后 `getInstance()` 将返回 `null`。
One instance is kept per element in a registry backed by a `WeakMap`, so instances are garbage-collected together with their elements (nothing to clean up on Hotwired Turbo navigations). The data API listens with **delegated document-level handlers**, which means toggles inside content inserted after page load — AJAX partials, Turbo Frames — work without any re-initialisation.
每个元素在注册表中只保留一个实例，该注册表基于 `WeakMap` 实现，因此实例会与其对应的元素一起被垃圾回收（在 Hotwired Turbo 导航时无需额外清理）。数据 API 使用**委托的 document 级事件处理器**进行监听，这意味着在页面加载后插入的内容（如 AJAX 局部更新、Turbo Frames）中的切换控件也无需重新初始化即可正常工作。

A language switcher wired to a real locale
一个与真实语言环境联动的语言切换器
The demo topbar ships a language dropdown, but the markup alone changes nothing — swapping the locale is the application's job, and doing it badly is worse than not shipping it. The pattern below covers what a switcher actually has to get right.
演示版的顶栏自带一个语言下拉菜单，但光有这点标记其实什么都变不了——切换语言区域是应用自己的活儿，而且做砸了还不如不做。下面这套模式涵盖了语言切换器真正必须做对的那些事。
Four things make the difference between a working switcher and set dressing:
四件事决定了语言切换器是真能用还是纯摆设：
1. **Each item is a real link to the same page in another locale**, not a `#` with a click handler. A link is bookmarkable, crawlable, opens in a new tab, and works before your JavaScript loads. Add `hreflang` so assistive tech announces the language change and search engines can pair the URLs.
1. **每一项都是一个真正的链接，指向同一页面在另一种语言区域下的版本**，而不是一个带点击事件的 `#`。链接可以被收藏、被爬虫抓取、能新标签页打开，而且在你的 JavaScript 加载之前就能用。再加上 `hreflang`，这样辅助技术能播报语言变化，搜索引擎也能把对应的 URL 配对起来。
2. **The locale belongs in the URL** (`/es/dashboard`) or in a cookie the server reads — not in `localStorage`. Server-rendered HTML has to know the locale *before* it renders, and `localStorage` is only readable after the page has already been sent in the wrong language.
2. **语言区域应该放在 URL 里**（比如 `/es/dashboard`），或者放在服务器能读取的 cookie 里——而不是放在 `localStorage` 里。服务端渲染的 HTML 必须在渲染*之前*就知道语言区域是什么，而 `localStorage` 要等页面已经以错误语言发出去了之后才能读到。
3. **Mark the current language** with both `.active` and `aria-current="true"`, and name it in the toggle's `aria-label`. A flag icon alone is not a language: several languages share a flag, and several countries share a language.
3. **标记当前语言**，同时用上 `.active` 和 `aria-current="true"`，并在切换按钮的 `aria-label` 里写明当前语言。光有一个国旗图标并不能代表一门语言：好几种语言共用一个国旗，也有好几个国家共用一门语言。
4. **Switching to an RTL locale needs the RTL stylesheet**, not just a `dir` attribute. Serve `adminlte.rtl.css` and set `<html lang="ar" dir="rtl">` together — see [RTL Support](rtl.html).
4. **切换到 RTL（从右到左）语言区域时，需要配套的 RTL 样式表**，光加个 `dir` 属性是不够的。要同时提供 `adminlte.rtl.css` 并设置 `<html lang="ar" dir="rtl">`——详见 [RTL 支持](rtl.html)。
If your locale lives in the URL, the server picks the stylesheet and the switcher stays pure markup:
如果你的语言区域放在 URL 里，那么由服务器来挑样式表，切换器本身就可以保持纯标记：
Rendered per request from the active locale
按请求、基于当前激活的语言区域实时渲染
For a client-rendered app, do the same work at the router level — change the locale, re-render, and swap the stylesheet `href` — rather than translating text nodes in place.
对于客户端渲染的应用，要在路由层面做同样的事——切换语言区域、重新渲染、替换样式表的 `href`——而不是就地去翻译文本节点。

##### Matching rules

- Matching is case-insensitive and matches anywhere in a `.nav-link`'s text, not just at the start.
- 匹配不区分大小写，而且在 `.nav-link` 的文字里任意位置都能匹配，不只是开头。
- A parent survives if any descendant matches, and is expanded to reveal it.
- 只要有一个后代匹配，父级就会保留下来，并且会被展开以露出那个匹配项。
- A parent whose own name matches keeps its entire subtree, so expanding it is never a dead end.
- 如果父级自己的名字就匹配上了，那它整棵子树都会保留，所以展开它绝不会是死路一条。
- `.nav-header` section labels are hidden while filtering, because the groups they label are no longer intact.
- 筛选期间，`.nav-header` 的区块标题会被隐藏，因为它们所标注的那些分组已经不再完整了。

- Entries are hidden with the `hidden` attribute, not a class, so they leave the accessibility tree as well as the layout. Nothing in your CSS has to know about the filter.
- 条目是用 `hidden` 属性隐藏的，而不是加个类，所以它们会同时从无障碍树和布局里消失。你的 CSS 完全不需要知道有筛选这回事。
- The plugin snapshots each submenu's open state *and* its inline `display` before the first keystroke. Both matter: [Treeview](treeview.html) writes an inline `display` while sliding a menu open or shut, and that would otherwise outrank `.menu-open > .nav-treeview` after a search.
- 插件会在你敲下第一个键之前，先把每个子菜单的展开状态*以及*它的内联 `display` 都拍个快照。这两样都重要：因为 [Treeview](treeview.html) 在滑动展开或收起菜单时会写入内联 `display`，否则搜索之后这个内联样式会盖过 `.menu-open > .nav-treeview` 的规则。

- 因为搜索会重写 `.menu-open`，所以在筛选生效期间，别用你自己的代码去操作同一批子菜单——先把筛选清掉再说。
- In the mini sidebar the field is hidden, since a text input can't render usefully in the rail. It returns on hover along with the labels it filters.
- 在迷你侧边栏模式下，这个输入框是隐藏的，因为一条窄窄的侧边栏里塞个文本输入框根本没法用。鼠标悬停时它会回来，连同它要筛选的那些标签一起显示。

##### Anatomy

AdminLTE 4 styles itself with Bootstrap 5.3's theme colours — `primary`, `success`, `danger`, `warning`, `info`, `secondary`, `light`, `dark` — and nothing else. That keeps `adminlte.css` small, but a dashboard often wants more than five hues on a widget row, and AdminLTE 3 users miss `.bg-navy`, `.bg-teal` and the sidebar skins.
AdminLTE 4 只用了 Bootstrap 5.3 的主题色来给自己做样式 —— `primary`、`success`、`danger`、`warning`、`info`、`secondary`、`light`、`dark` —— 除此之外没别的。这让 `adminlte.css` 保持得很小，但仪表盘的一行组件里经常想要不止五种色调，而且 AdminLTE 3 的老用户还惦记着 `.bg-navy`、`.bg-teal` 和那些侧边栏皮肤。
**`dist/css/adminlte-colors.css`** is the answer, and it is opt-in: one extra stylesheet (≈ 8 kB gzipped) that adds fourteen colours as `--bs-*` tokens plus every class family Bootstrap generates for its own theme colours — and lets any of them [become your `primary`](#making-one-of-them-your-primary). Nothing changes for projects that don't load it. Prefer the AdminLTE 3 colours exactly as they were? There is a second sheet for that — see [Two palettes](#two-palettes) below.
**`dist/css/adminlte-colors.css`** 就是答案，而且是按需启用的：多加载一个样式表（gzip 后约 8 kB），就会以 `--bs-*` token 的形式加入十四种颜色，外加 Bootstrap 为自己主题色生成的那一整套类系列 —— 而且还能让其中任意一个[成为你的 `primary`](#making-one-of-them-your-primary)。对于不加载它的项目来说，什么都不变。更喜欢 AdminLTE 3 原封不动的颜色？还有一个专门的样式表 —— 见下面的[两套调色板](#two-palettes)。

##### How the palette was designed
##### 这套调色板是怎么设计出来的
The fourteen values are generated, not picked. `scripts/palette.mjs` derives them in **OKLCH** — the perceptually uniform colour space Tailwind v4 and Radix build their palettes in — from three rules:
这十四个值不是手工挑出来的，而是生成出来的。`scripts/palette.mjs` 是在 **OKLCH** 里把它们推导出来的 —— OKLCH 是 Tailwind v4 和 Radix 用来构建各自调色板的那种感知均匀色彩空间 —— 依据的是三条规则：

<li class="mb-3"><strong>Equal contrast, by construction.</strong> Each chromatic colour is the <em>lightest</em> value of its hue whose white text still reaches 4.6:1. That puts every one at OKLCH L ≈ 0.55–0.59 — the same visual weight as Bootstrap's own primary, success and danger — so a row of mixed widgets never has one colour shouting.</li>
<li class="mb-3"><strong>对比度一致，是设计使然。</strong>每一种彩色，都是它那个色相下白色文字仍能达到 4.6:1 的<em>最浅</em>取值。这就让它们全都落在 OKLCH L ≈ 0.55–0.59 —— 和 Bootstrap 自己的 primary、success、danger 视觉分量相同 —— 所以一行混搭的组件里，不会有一个颜色特别扎眼。</li>
<li class="mb-3"><strong>Hues in the gaps.</strong> Bootstrap already owns red (21°), yellow (85°), green (157°), cyan (218°) and blue (260°). The palette hues sit at least 17° from each of them and 20° from each other — orange 42 · amber 67 · olive 126 · teal 190 · sky 237 · indigo 283 · violet 303 · fuchsia 324 · pink 350 — so mixing palette and theme colours on one page is safe.</li>
<li class="mb-3"><strong>色相落在空档里。</strong>Bootstrap 已经占了红（21°）、黄（85°）、绿（157°）、青（218°）和蓝（260°）。调色板的色相跟它们每一个都至少差 17°，彼此之间至少差 20° —— orange 42 · amber 67 · olive 126 · teal 190 · sky 237 · indigo 283 · violet 303 · fuchsia 324 · pink 350 —— 所以在同一个页面里混用调色板和主题色是安全的。</li>
<li class="mb-0"><strong>Chroma capped, neutrals tinted.</strong> Chroma is capped at 0.20 (parity with primary 0.23 / danger 0.20), so indigo and violet don't overpower teal and amber, which sit at the sRGB gamut limit for this lightness. The five neutrals — navy, steel, slate, graphite, midnight — are cool-tinted (hue ≈ 255–287°) rather than pure grey, the way modern UI neutrals are built, and sit at the lightness steps popular admin kits use for their sidebars (L ≈ 0.24, 0.30, 0.33, 0.40, 0.50).</li>
<li class="mb-0"><strong>彩度设了上限，中性色带点色调。</strong>彩度上限设在 0.20（和 primary 的 0.23 / danger 的 0.20 持平），这样 indigo 和 violet 就不会盖过 teal 和 amber，因为后两者在这个明度下已经贴到 sRGB 色域边界了。那五种中性色 —— navy、steel、slate、graphite、midnight —— 都是偏冷的色调（色相 ≈ 255–287°），而不是纯灰，这也是现代 UI 中性色的做法；它们的明度档位也正好是流行后台套件用来做侧边栏的那几档（L ≈ 0.24、0.30、0.33、0.40、0.50）。</li>

##### Accessibility and dark mode
##### 无障碍与深色模式
- Every colour in the **designed** palette clears 4.5:1 with white text (the lowest is 4.6:1), so `.text-bg-*` never needs a per-colour exception and the demo pages using them pass the axe gate.
- **重新设计的**那套调色板里，每种颜色配白色文字都能达到 4.5:1（最低的是 4.6:1），所以 `.text-bg-*` 从不需要为某个颜色单独开例外，用到它们的演示页面也都能通过 axe 检查关卡。

##### Charts that follow dark mode
##### 会跟随深色模式的图表
Charting libraries draw their own text and tooltips, so they know nothing about `data-bs-theme`. ##### Printing a page as a document
##### 将页面作为文档打印
AdminLTE prints the whole layout — sidebar, header and content — with the styles you would want for reading a copy of a screen: the target of an external link is printed after it, buttons keep an outline so they still read as buttons, and everything goes black on white so backgrounds don't eat ink.
AdminLTE 会打印完整布局——侧边栏、头部与内容区，采用适合复刻屏幕画面阅读的样式：外部链接会在文本后打印链接地址，按钮保留外轮廓，维持按钮的视觉识别效果，整体采用黑字白底，避免背景消耗墨水。
For pages that print as *documents* — an invoice, quote, work order or packing slip that goes to a customer — that is the wrong output: nobody wants `Pay online (https://pay.example.com/inv/12345?token=…)` on a printed invoice, or a box drawn around a button. **`data-lte-contrast="aa"` 能修好这八种颜色，而且一个取值都不用动。** v3 的规则给八种颜色配了白色文字，而这八种颜色对正文来说都达不到 WCAG AA 的 4.5:1。这个属性只把这八种翻成能达到标准的深色文字，每一个背景色都保持一个字节不变：
The ratios are stated rather than shown, because rendering the failing combination would put text on this page that fails the same check — flip the switch on the <a href="../UI/colors.html">Colors demo</a> to see both side by side on real components. It covers everywhere the palette paints text on its own colour: `.text-bg-*`, `.bg-gradient-*`, `.card-*` headers, `.direct-chat-*`, and the button, badge and pill text that `data-lte-primary` produces. Three things worth knowing:
这里只列出比值，而不是把它们渲染出来，因为把不达标的组合渲染出来，就等于在本页面上放了同样通不过这项检查的文字 —— 去 <a href="../UI/colors.html">颜色演示</a> 页面把开关打开，就能在真实组件上看到两者并排对比。它覆盖了调色板在自己颜色上绘制文字的所有地方：`.text-bg-*`、`.bg-gradient-*`、`.card-*` 头部、`.direct-chat-*`，以及 `data-lte-primary` 生成的按钮、徽章和胶囊文字。有三件事值得了解：
- **It has to be black.** AdminLTE 3's own dark ink, `#1f2d3d`, only clears 4.5:1 on two of the eight — `teal` and `cyan`. The others need true black, which is what `aa` uses. The colours that already take dark text (`lime`, `orange`, `yellow`) keep `#1f2d3d` and are not touched.
- **必须用纯黑。** AdminLTE 3 自己的深墨色 `#1f2d3d` 在这八种颜色里只有两种能达到 4.5:1 —— `teal` 和 `cyan`。其余的都需要纯黑，也就是 `aa` 用的那个。本来就配深色文字的那些颜色（`lime`、`orange`、`yellow`）继续用 `#1f2d3d`，不动它们。
- **Pair a flipped colour with `data-bs-theme="light"`.** A sidebar or header carrying one of the eight now has dark text, so its nav links should follow: `<nav class="app-header navbar navbar-expand text-bg-lightblue" data-bs-theme="light">`. The demo pages do this for you when the switch is on.
- **翻转过的颜色要搭配 `data-bs-theme="light"`。** 承载这八种颜色之一的侧边栏或头部现在用的是深色文字，所以它的导航链接也应该跟着变：`<nav class="app-header navbar navbar-expand text-bg-lightblue" data-bs-theme="light">`。演示页面在开关打开时会帮你处理好这件事。
- **`.text-lightblue` and `.link-lightblue` are a different question.** Those paint the colour *as text on the page background*, where the same eight are also thin. Use the emphasis token instead — `.text-lightblue-emphasis` equivalents come from `--bs-lightblue-text-emphasis`, which is the colour shaded 60% and readable on a light background.
- **`.text-lightblue` 和 `.link-lightblue` 是另一个问题。** 那些是把颜色*当作文字画在页面背景上*，而这八种颜色在那里同样也不够。改用 emphasis token 吧 —— `.text-lightblue-emphasis` 这类写法来自 `--bs-lightblue-text-emphasis`，也就是把这个颜色调暗 60% 之后的结果，在浅色背景上能看清。
The attribute works with either sheet; on the designed palette it emits nothing at all, because every colour there clears AA with white text by construction — so it costs nothing to leave in your markup ([#6110](https://github.com/ColorlibHQ/AdminLTE/issues/6110)).
这个属性对两个样式表都有效；在重新设计的那套调色板上，它什么都不输出，因为那里的每种颜色按构造就配白色文字达到了 AA —— 所以把它留在你的标记里没有任何开销（[#6110](https://github.com/ColorlibHQ/AdminLTE/issues/6110)）。
